# SHAP Explainability System Documentation
**Project**: Fraud Detector  
**Component**: Decision Engine Explanation Layer  
**Date**: 2025-12-14

## 1. Overview
The system employs a **Shape-Aware Explainability Layer** that goes beyond standard SHAP feature attribution. It combines a canonical explanation model (`ExtraTrees_uncalibrated`) with a pre-computed **Trend Registry** and **Categorical Parsing Logic** to generate human-readable, context-aware risk narratives.

## 2. Architecture & Data Flow

### 2.1 Trend Registry (Offline)
*   **Script**: `fraud-detector/build_trend_registry.py`
*   **Artifact**: `fraud-detector/models/trend_registry.json`
*   **Purpose**: 
    - Maps the non-linear risk profile (SHAP response curve) of continuous features.
    - Identifies if a specific value range (e.g., "Low Injury Share") is risky relative to the average.
    - Enables "U-shape" awareness (e.g., distinguishing "Safe Mid-Range" from "Risky Extremes").

### 2.2 Runtime Explanation Logic (`app.py`)
The explanation pipeline follows these steps:

1.  **Canonical Source**: All requests (regardless of the predictive model used) fetch explanations from a fixed logical source (`ExtraTrees_uncalibrated`) to ensure consistent interpretation.
2.  **SHAP Computation**: Computes raw SHAP values for the top driving features.
3.  **Refinement Layer**:
    *   **Categorical Parsing**: 
        *   Detects specific categories (e.g., "authorities_contacted_Ambulance").
        *   Translates to natural text: "Contacting Ambulance" instead of generic "Authorities Contacted".
        *   Handles missing data: "No Authorities Contacted", "Unknown Collision Type".
    *   **Shape-Aware Narratives**:
        *   Consults `trend_registry.json` for continuous features.
        *   Compares the current value's risk to the typical risk.
        *   Generates nuanced text like "**Low** Injury Share is associated with **higher risk than average**".

### 2.3 Frontend Integration (`index.html`)
*   **Feedback Loop**: The UI catches network errors (Connection Refused) and prompts the user to check the API.
*   **Rendering**: Displays the *exact* text generated by the backend, ensuring backend logic (like specific category names) is respected.

## 3. Key Improvements

### 3.1 Shape Awareness
Standard SHAP only says "Risk Up/Down". Our system adds context:
| Feature | Value | Old Text | New Shape-Aware Text |
| :--- | :--- | :--- | :--- |
| `injury_share` | `0.01` | "Increases Risk" | "**Low** Injury Cost Portion is associated with **higher risk than average**" |
| `incident_hour` | `0` | "Reduces Risk" | "**Low** Incident Time is associated with **lower risk**" |

### 3.2 Polished Categorical Phrasing
Handles grammar and specificity for categorical flags:
*   "**Contacting Police** reduces risk estimate" (Specific)
*   "**No Authorities Contacted** contributes to risk" (Natural Phrasing for 'None')
*   "**Unknown Collision Type**" (Handles missing data '?')
*   "**Police Report: Available**" (Handles Boolean-like flags)

### 3.3 Robustness
*   **Lazy Loading**: The system logs model loading errors instead of crashing, exposing them via `/health`.
*   **Safety Net**: If SHAP filtering returns no drivers (rare edge case), a fallback explanation "No significant drivers found" is returned to prevent UI errors.

## 4. Operational Maintenance
*   **Registry Updates**: If the underlying model or data distribution changes significantly, run `python build_trend_registry.py` to update the risk curves.
*   **Feature Map**: Add new features to `FEATURE_MAP` in `app.py` to define their user-friendly labels.
